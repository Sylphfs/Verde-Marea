# RUNBOOK — Verde Marea (развёртывание, проверка, приёмка)

Этот документ описывает, как развернуть проект локально, проверить его и безопасно обновлять.

## 1. Требования к окружению

- Node.js ≥ 23.6 (рекомендуется 24; seed запускается встроенным TypeScript-рантаймом Node).
- npm (входит в состав Node.js).
- PostgreSQL 14+ (проект проверялся на PostgreSQL 16).
- Терминал (PowerShell или cmd на Windows).

Проверка версий:

```bash
node -v
npm -v
psql --version
```

## 2. Подготовка окружения (один раз)

1. Установить Node.js и PostgreSQL, если их нет.
2. Убедиться, что сервер PostgreSQL запущен (служба `postgresql-x64-16` на Windows).
3. Знать логин и пароль суперпользователя PostgreSQL. По умолчанию `postgres` / `postgres`; если пароль другой — указать его в файле `.env` (см. шаг 2 первого запуска).

## 3. Первый запуск

Из корня проекта:

```bash
# 1) зависимости
npm install

# 2) файл окружения (на Windows: copy .env.example .env)
cp .env.example .env

# 3) создать базу (пароль по запросу; по умолчанию postgres)
psql -U postgres -h localhost -c "CREATE DATABASE verde_marea;"

# 4) применить миграции (создаст таблицы и сгенерирует Prisma-клиент)
npx prisma migrate dev --name init

# 5) контрольные данные (столы, окна на 14 дней, super_admin, гость, демо-брони)
npx prisma db seed

# 6) запустить приложение
npm run dev
```

Открыть http://localhost:3000.

### Если PowerShell ругается на npm.ps1

```
npm.ps1 cannot be loaded because running scripts is disabled on this system.
```

Выполнить один раз:

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

или использовать `npm.cmd` / `npx.cmd` вместо `npm` / `npx`.

### Скрипты package.json

| Команда | Что делает |

## 4. Учётные записи и роли

Seed создаёт:

| Роль | Email | Пароль |
|---|---|---|
| super_admin | admin@verdemarea.local | Admin123! |
| user | guest@verdemarea.local | Guest123! |

### Как создать пользователя нужной роли

- **user** — зарегистрироваться через `/register` (роль `user` назначается по умолчанию).
- **admin** — войти как super_admin → «Админ-панель» → «Пользователи» → выбрать у пользователя роль `admin` → «Сохранить».
- **super_admin** — аналогично, выбрать роль `super_admin` (или использовать seed-аккаунт `admin@verdemarea.local`).

## 5. Сценарий базовой локальной проверки

Сквозной сценарий (запуск → … → история изменений):

1. **Запуск**: `npm install` → `cp .env.example .env` → `CREATE DATABASE` → `npx prisma migrate dev --name init` → `npx prisma db seed` → `npm run dev`. Открыть http://localhost:3000.
2. **Регистрация**: `/register` → создать гостя (роль user). После создания — редирект в «Личный кабинет».
3. **Вход**: выйти и войти под созданным пользователем (или под `guest@verdemarea.local`).
4. **Бронирование**: «Забронировать стол» → дата (вт–вс, в пределах 14 дней) и число гостей → «Показать окна» → «Забронировать» на свободном окне. Результат: статус `Ожидает`, назначен стол, редирект на «Мои бронирования».
5. **Уведомления**: «Кабинет» → «Уведомления» — есть запись о создании брони.
6. **Отмена**: «Мои бронирования» → «Отменить» (доступно за ≥ 3 часа до начала). После дедлайна кнопки нет, сервер отклоняет отмену.
7. **Администратор**: войти как `admin@verdemarea.local` → «Админ-панель» → «Бронирования» → подтвердить бронь (статус → `Подтверждена`), затем «Завершить» или «Неявка».
8. **Изменение роли**: «Пользователи» → повысить гостя до `admin` → «Сохранить».
9. **История изменений**: «История» → видны записи о создании, подтверждении, отмене, завершении, неявке брони и смене роли (кто и когда).

## 6. Обновление после изменений

### Изменение схемы данных (`prisma/schema.prisma`)

```bash
npx prisma migrate dev --name <имя_изменения>
npx prisma db seed   # при необходимости обновить данные
npm run dev
```

### Изменение только серверной или клиентской логики (без схемы)

```bash
npm run dev   # dev-сервер Next.js подхватывает изменения сам
```

### Что обязательно перепроверить после изменений

- **Доступность/окна** → проверить: создание брони, назначение стола, защиту от дублей, список броней у администратора.
- **Роли** → проверить: пользовательский контур, admin, super_admin и историю изменений.

## 7. Чек-лист локальной приёмки

- [ ] `npm install` проходит без ошибок; есть `node_modules` и `package-lock.json`.
- [ ] Есть `.env.example`; реальный `.env` не хранится в проекте (создаётся локально копированием).
- [ ] `npx prisma migrate dev` применяет миграцию (папка `prisma/migrations` непустая).
- [ ] `npx prisma db seed` создаёт столы, окна, super_admin и гостя.
- [ ] Регистрация и вход работают; пароль в БД — только `passwordHash` (bcryptjs, 12 раундов).
- [ ] `passwordHash` не возвращается в UI и API.
- [ ] Гость не попадает в `/admin`; admin не видит «Историю» и не меняет роли.
- [ ] Бронирование: только валидные окна (14 дней, вт–вс, 12:00–21:00, не прошедшие, со свободным подходящим столом).
- [ ] Дубли запрещены: один пользователь — одна активная бронь на окно; один стол — одна бронь на окно.
- [ ] Бронь создаётся со статусом `pending` и назначенным столом.
- [ ] Отмена пользователем — не позднее 3 часов; после дедлайна недоступна.
- [ ] Админ: фильтры по статусу и дате, виден стол и статус `no_show`, переходы по машине состояний, терминальные статусы не возвращаются в активные.
- [ ] История изменений: создание/подтверждение/отмена/завершение/неявка/смена роли — с автором и временем.
- [ ] Уведомления создаются и отображаются в «Кабинете».
- [ ] Интерфейс соответствует design.md (цвета, шрифты, компоненты).
