# Verde Marea — система бронирования столов

Локальный учебный проект: система бронирования столов в ресторане Verde Marea.

## Быстрый старт (локально)

Полная инструкция по развёртыванию, проверке и обновлению — в [RUNBOOK.md](RUNBOOK.md). Коротко:

```bash
npm install
cp .env.example .env        # на Windows: copy .env.example .env
psql -U postgres -h localhost -c "CREATE DATABASE verde_marea;"
npx prisma migrate dev --name init
npx prisma db seed
npm run dev
```

Открыть http://localhost:3000. Вход: `admin@verdemarea.local / Admin123!` (super_admin), `guest@verdemarea.local / Guest123!` (user).

## Легенда

Verde Marea («зелёная волна») — семейный ресторан средиземноморской кухни на берегу моря. Название соединяет два образа: оливковые рощи и морскую волну. Кухня — свежие морепродукты, сезонные овощи и травы, домашняя паста, небольшая винная карта.

Зал небольшой, мест мало, поэтому гости бронируют столик заранее. Атмосфера — спокойная, камерная, «тихая роскошь»: приглушённый свет, натуральное дерево, тёплая кремовая гамма с тёмно-зелёными и золотыми акцентами.

Система помогает гостю выбрать свободное окно и стол, а персоналу — управлять бронями.

## Состав MVP

- Регистрация и вход по email и паролю (пароль — только как bcrypt-хэш, 12 раундов).
- Просмотр доступных окон бронирования на ближайшие 14 дней (вт–вс, шаг 90 минут, 12:00–21:00).
- Бронирование стола на выбранное окно.
- Отмена собственной брони — не позднее чем за 3 часа до начала.
- Просмотр списка своих броней.
- admin: просмотр всех броней, подтверждение/отмена, отметки completed и no_show.
- super_admin: управление ролями пользователей, просмотр журнала действий (AuditLog).
- Служебные уведомления внутри системы (без email/sms).

## Граница MVP (чего НЕ делаем)

- Никаких внешних интеграций: платежи, email, sms, внешние календари, аналитика, гео-сервисы.
- Никакого публичного деплоя: всё работает локально.
- Без лишнего «продакшен-контура»: CI/CD, оркестрация, мониторинг, масштабирование не нужны.
- Уведомления — только внутри приложения, без внешних провайдеров.

## Роли

| Роль | Назначение |
|------|------------|
| user | Гость: бронирует и отменяет свои брони. |
| admin | Персонал: управляет всеми бронями и статусами. |
| super_admin | Владелец: управляет ролями и читает AuditLog. |

## Правила доступа

- user: регистрация/вход, просмотр свободных окон, создание брони, отмена своей брони (за ≥ 3 часа), просмотр своих броней.
- admin: всё, что умеет user, плюс просмотр всех броней и пользователей, изменение статусов броней (confirmed / cancelled / completed / no_show).
- super_admin: всё, что умеет admin, плюс назначение ролей и просмотр AuditLog.
- Пользователь видит только свои брони; чужие данные недоступны.
- passwordHash не возвращается в UI и API никогда.

## Сценарии

### Пользовательские
1. Регистрация и вход.
2. Просмотр свободных окон на дату (видны только доступные слоты).
3. Бронирование стола на выбранное окно.
4. Отмена своей брони (не позднее 3 часов до начала).
5. Просмотр списка своих броней и их статусов.

### Административные
1. Просмотр всех броней с фильтрами по дате и статусу.
2. Подтверждение брони (pending → confirmed).
3. Отметка завершения (confirmed → completed) и неявки (confirmed → no_show).
4. Отмена брони администратором.
5. super_admin: смена роли пользователя, просмотр AuditLog.

### Служебные
1. Генерация слотов на 14 дней и начальных столов (seed).
2. Запись значимых действий в AuditLog.
3. Создание уведомлений при изменении статуса брони.
