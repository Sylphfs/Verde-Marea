# Модель данных и правила Verde Marea

Этот документ переводит продуктовую рамку (README.md) в схему данных и правила,
которые реализуются на сервере. Схема описана в `prisma/schema.prisma`.

## Сущности

| Сущность | Назначение |
|----------|------------|
| User | Пользователь с ролью user / admin / super_admin. Пароль — только passwordHash. |
| Table | Стол с номером и вместимостью. |
| Slot | Окно бронирования (90 минут) в рамках рабочего графика. |
| Booking | Бронь: гость + окно + стол + число гостей + статус. |
| Notification | Служебное уведомление для пользователя. |
| AuditLog | Журнал изменений (кто, что и когда сделал). |
| Session | Сессия пользователя (токен в httpOnly-cookie, время жизни 7 дней). |

## Связи

- User 1—N Booking (все брони гостя).
- Table 1—N Booking, Slot 1—N Booking.
- Booking 1—N Notification (опциональная привязка уведомления к брони).
- User 1—N AuditLog (как инициатор действия; история сохраняется, даже если аккаунт удалён).
- User 1—N Session (сессии входа).

## Матрица ролей

| Действие | user | admin | super_admin |
|----------|:----:|:-----:|:-----------:|
| Регистрация / вход | ✓ | ✓ | ✓ |
| Просмотр своих броней | ✓ | ✓ | ✓ |
| Создание брони | ✓ | ✓ | ✓ |
| Отмена своей брони (за ≥ 3 ч) | ✓ | ✓ | ✓ |
| Просмотр всех броней | ✗ | ✓ | ✓ |
| Подтверждение (pending → confirmed) | ✗ | ✓ | ✓ |
| Отмена любой брони (в любое время) | ✗ | ✓ | ✓ |
| Отметка completed / no_show | ✗ | ✓ | ✓ |
| Просмотр списка пользователей | ✗ | ✓ | ✓ |
| Управление столами | ✗ | ✓ | ✓ |
| Смена роли user ↔ admin | ✗ | ✗ | ✓ |
| Назначение / снятие роли super_admin | ✗ | ✗ | ✓ |
| Просмотр AuditLog | ✗ | ✗ | ✓ |

Ключевое правило: **admin не управляет ролью super_admin** — ни назначить, ни снять.
Ролями (включая super_admin) управляет только super_admin.

## Правила вместимости столов

- У брони всегда указано число гостей `guests`.
- Правило: `guests <= table.capacity`.
- «Подходящий стол» — стол, у которого `capacity >= guests`.

## Правила доступности окон

Окно брони доступно, только если выполнены **все** условия:

1. Окно в пределах ближайших 14 дней.
2. День недели — со вторника по воскресенье (понедельник — выходной).
3. Шаг окон — 90 минут.
4. Диапазон — 12:00–21:00: старты слотов 12:00, 13:30, 15:00, 16:30, 18:00, 19:30 (последний заканчивается в 21:00).
5. Время не в прошлом (`slot.startTime > now`).
6. Окно не занято: в нём есть хотя бы один свободный подходящий стол.
7. Наличие подходящего стола обязательно (п. «Вместимость»).

## Дедлайн отмены

- Пользователь может отменить **свою** бронь не позднее чем за **3 часа** до начала окна.
- После дедлайна отменить может только admin (в любое время).
- Проверка дедлайна — строго на сервере.

## Защита от дублей (на сервере, в транзакции)

Перед созданием/переносом брони сервер проверяет:

1. **Один стол — одно активное бронирование на окно.** Для пары (slot, table) не должно быть другой активной брони.
2. **Один пользователь — одно активное бронирование на окно.** Пользователь не может занять два стола в одно и то же окно.

«Активная» бронь — со статусом `pending` или `confirmed`. Статусы `cancelled`, `completed`, `no_show` освобождают окно и стол.

## Машина состояний брони

Статусы: `pending`, `confirmed`, `cancelled`, `completed`, `no_show`.

| Из | В | Кто и когда |
|----|---|-------------|
| pending | confirmed | admin |
| pending | cancelled | пользователь (за ≥ 3 ч) или admin (в любое время) |
| confirmed | completed | admin |
| confirmed | no_show | admin |
| confirmed | cancelled | пользователь (за ≥ 3 ч) или admin (в любое время) |
| cancelled / completed / no_show | — | терминальные состояния |

## Как seed восстанавливает сценарии

`prisma/seed.ts` создаёт:

- 4 стола разной вместимости (2, 2, 4, 6 мест) — для проверки «подходящего стола».
- super_admin: `admin@verdemarea.local / Admin123!`.
- демо-гостя: `guest@verdemarea.local / Guest123!`.
- окна на ближайшие 14 дней по правилам (вт–вс, шаг 90 мин, 12:00–21:00).
- две демо-брони (confirmed и pending) на разные окна и разные столы.

## Аутентификация и сессии

- Пароль хранится только как `passwordHash` (bcryptjs, 12 раундов); открытый пароль, MD5/SHA и самописная соль не используются.
- Регистрация: `bcryptjs.hash(password, 12)`. Вход: `bcryptjs.compare(password, user.passwordHash)`.
- Сессия — строка `Session` в БД + случайный токен (`node:crypto`, 32 байта), передаётся в httpOnly-cookie `session`.
- Время жизни сессии — 7 дней; выход удаляет строку сессии и очищает cookie.
- `passwordHash` не выбирается и не возвращается ни в UI, ни в API (запросы используют `select` без этого поля).

## Ролевая логика (клиент и сервер)

- Единый источник правил — `lib/roles.ts` (список ролей, матрица прав, `can()` и `canSetRole()`).
- Сервер — авторитетный: `requireRole()` в страницах и проверки в server actions блокируют запрещённые действия (redirect или ошибка).
- Клиент использует `lib/roles.ts` только для видимости элементов (показать/скрыть), но не для защиты.
- Роль меняет только `super_admin`; обычный `admin` не может менять роли, в том числе роль `super_admin`.
- Защита от блокировки: нельзя понизить единственного `super_admin`.
- Смена роли фиксируется в `AuditLog` (action `user.role_changed`).
